# Contributing to mysql_samp

Thanks for wanting to help. This page is the short version of how the project
is built and what a change has to satisfy before it can be merged.

## Before you start

For a bug, open an issue with the server it happened on, the plugin version and
what the log said — the templates ask for exactly that. For a feature, say what
you were trying to do first: the API is deliberately small, and the question
that decides a new native is whether the common case still fits in two lines.

**Never paste a real database password, a real connection string or an
unredacted `logs/mysql.log`.** Replace the credential with `xxx` before you
attach anything, and remember that a syntax error echoes a fragment of the
statement that produced it.

## Setting up

**Prerequisites:**

```bash
rustup target add i686-unknown-linux-gnu i686-pc-windows-msvc
sudo apt install gcc-multilib g++-multilib      # the TLS backend builds 32-bit C
```

The plugin is 32-bit: build and test with the target, not with a bare `cargo`.

```bash
cargo build --target i686-unknown-linux-gnu
cargo test  --target i686-unknown-linux-gnu
```

**Required before a pull request:**

```bash
cargo fmt --all -- --check
cargo clippy --target i686-unknown-linux-gnu --all-targets -- -D warnings
cargo test --target i686-unknown-linux-gnu
python3 .github/scripts/check_pawn_encoding.py
```

The examples have to compile clean as well — exit 0 **and** no diagnostics.
They need `include/mysql_samp.inc`, which `cargo build` generates, plus your
server's own includes (`a_samp.inc` and friends):

```bash
for f in examples/*.pwn; do
  out=$(pawncc "$PWD/$f" -i"$PWD/include" -i/path/to/server/qawno/include \
        -o"/tmp/$(basename "$f" .pwn).amx" 2>&1) || echo "FAILED: $f"
  echo "$out" | grep -E 'warning|error' && echo "  in $f"
done
```

Check the exit code, and never send the output to `/dev/null`: `pawncc`
segfaults on `-o/dev/null` without printing anything, so a loop that only
greps for errors reports success for a file that never compiled.

## Rules that are easy to trip on

- **`include/mysql_samp.inc.in` is the source.** `include/mysql_samp.inc` and
  `include/mysql_samp_omp.inc` are generated by `build.rs` and overwritten on
  every build; a change made there disappears.
- **A new native touches four places:** the file under `src/natives/`, the list
  in `src/lib.rs`, the declaration in the `.inc.in` (in its section, with a
  JavaDoc block) and an example that calls it. `tests/inc_natives.rs` compares
  the first two against the include and fails when they drift, so a forgotten
  declaration stops the build instead of becoming a native Pawn cannot reach.

  To see the list the plugin actually registers, start a server with

  ```bash
  SAMP_PAWN_INCLUDE=/tmp/generated.inc ./samp03svr
  ```

  and rust-samp writes a declaration for every `#[native]`. The ones declared
  `raw` — our variadic natives — come out commented, since their arity is not
  in the signature. It is a cross-check by hand, not a replacement for the
  `.inc.in`, which carries the Pawn tags, the enums and the JavaDoc that the
  generated file has no way to know about.
- **The natives page is generated, not written.** `docs/natives.md` is built
  from the includes by `scripts/gen_natives_page.py` on every docs build, so
  it is not in the repository and editing it is pointless. What reaches that
  page is the JavaDoc block in `include/mysql_samp.inc.in` - including
  `@example`, which becomes a code block. Native names inside a comment are
  rewritten for the open.mp include, so an example can name a native and still
  read correctly in both files.

  ```bash
  python3 scripts/gen_natives_page.py             # write docs/natives.md
  python3 scripts/gen_natives_page.py --check     # fail if an entry has no doc block
  python3 scripts/gen_natives_page.py --selftest  # parser fixtures, JavaDoc and pawndoc
  ```

  Both comment formats are understood: JavaDoc (`@param`, `@return`) and
  pawndoc (`<summary>`, `<param name="">`, `<returns>`). The includes here use
  JavaDoc; pawndoc is covered because a project is likely to pull in includes
  that use it.

- **Pawn sources are pure ASCII.** No accents, no typographic dashes, no curly
  quotes — the compiler reads bytes, and mojibake reaches the player instead of
  failing the build. Markdown is the exception, and the CI guard enforces the
  rest.
- **`pawncc` does not parse a function nothing calls.** Every function in an
  example is reached from a command or a callback; one without a caller was
  never verified, whatever the compiler said.
- **Nothing blocks the server tick.** There is no synchronous query native and
  reintroducing one is not on the table — a query that blocks freezes every
  player. Background work goes through the existing worker threads.
- **Ordering is a property of callbacks, not of execution.** `mysql_query`
  dispatches callbacks in submission order, but the statements themselves run
  concurrently, each on its own connection. Anything that must be serialised
  belongs in `mysql_query_file` or a transaction.
- **Tests must run without a database.** The suite is pure unit tests; a test
  that needs a live server is marked `#[ignore]` and says so, like the TLS one.
- **Code, comments, logs, documentation and the include are en-US.** Commit
  messages are in Portuguese.

## Where things live

```
src/            the plugin: natives/ is the Pawn surface, the rest is the engine
include/        the Pawn include (.inc.in is the source; the other two are built)
examples/       one runnable gamemode per topic
benchmark/      the comparison gamemodes and their fixtures
docs/           the documentation site
tests/          what has to hold from outside the crate, such as the includes
scripts/        the release builds, for Linux and for Windows
.github/        CI: build, tests, clippy, audit, CodeQL, encoding guard, docs
```

## Opening a pull request

- One subject per pull request, with the reasoning in the description: what was
  happening, why this fix and not another.
- Add the test that would have caught the bug. A change to a parser is worth a
  case in its module; a change to the includes is worth one in `tests/`.
- Update the documentation in the same change, so the two never drift.
- CI has to be green: build, tests, clippy with `-D warnings`, rustfmt, the
  encoding guard, CodeQL and the dependency audit.

## Reporting a security issue

Do not open a public issue. See [SECURITY.md](SECURITY.md).
